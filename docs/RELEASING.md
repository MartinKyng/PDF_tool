# Releasing PDF Tool

PDF Tool releases are desktop artifacts, not Python distributions.

## Version source

Edit only [`pdf_tool/version.py`](../pdf_tool/version.py):

```python
__version__ = "0.2.0"
```

Use semantic versioning (`MAJOR.MINOR.PATCH`). The app label, PyInstaller
build output, installer name and GitHub Release tag all read this value. Do
not add a second version file or hard-code a release version in a workflow.

## Stable release

1. Finish and test the change on a feature branch.
2. Change `__version__` in `pdf_tool/version.py` if the release version needs
   to advance.
3. Open and merge the pull request into `main`.
4. The `Desktop release` workflow automatically builds all three platforms.
5. A push to `main` publishes `v<version>` as the stable GitHub Release.

The Windows matrix job also creates the Inno Setup installer. If the same
version is pushed to `main` again, GitHub Actions updates that release; bump
the version before publishing a new stable release.

## Beta release

Every push to a non-main branch builds a GitHub prerelease:

```text
v<version>-beta.<github-run-number>
```

The suffix is generated by CI and does not modify the working tree. Beta
assets are for testing and are never marked as the latest stable release.
A manual workflow dispatch follows the same main-versus-other-branch rule.

## Before changing scope

The stable MVP currently means joining two or more PDFs. Do not add splitting,
rotation, page deletion, annotations or conversion as incidental release work.
Those features should be planned after the first usable stable version has
been explicitly accepted.
